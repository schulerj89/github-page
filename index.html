Recover

Map the machine before rewriting it.

Bank-aware disassembly, Ghidra analysis, emulator traces, and targeted scripts identify routines, data tables, timing rules, and state transitions.

02

Translate

Rebuild the behavior, not the hardware.

Original state machines and fixed-point rules become maintainable C and Win32 systems. The runtime does not contain a console emulator or read the ROM.

03

Verify

Compare every claim against evidence.

Deterministic tests, reference captures, trace comparisons, and machine-readable coverage gates separate verified parity from native approximations and open work.

03 / Working approach

A builder’s feedback loop.

Leadership works better when the plan stays connected to the product, the code, and the evidence.

  1. 01

    Frame the ambiguity.

    Turn a fuzzy problem into constraints, risks, decisions, and a first testable slice.

    FRAME
  2. 02

    Keep the system legible.

    Choose architecture and interfaces the next teammate can understand, change, and own.

    BUILD
  3. 03

    Validate the loop.

    Use tests, screenshots, telemetry, and real usage to replace assumptions with evidence.

    VERIFY
  4. 04

    Ship ownership, not output.

    Release work that the team can operate, explain, maintain, and improve after launch.

    SHIP

04 / About

Leadership with a builder’s feedback loop.

I’m at my best when the problem is still messy: turning it into a plan, keeping the architecture understandable, and building enough myself to stay close to the tradeoffs.

I’ve spent 15+ years shipping production software and leading engineering teams. Reverse-engineering ports keep my feedback loop honest: they force precise reasoning, explicit evidence, low-level systems work, and clear statements about what is known.

I also contribute upstream to Laravel and PHP documentation and build simulation, developer-tooling, and interactive projects across C, TypeScript, Go, and Rust.
